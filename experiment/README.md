# 统一射线路径的静态场景验收

这里验证完整立方体与格内复杂模型能否共用同一条遍历和合成路径。性能读数用于判断可用性和定位瓶颈，不以超过传统网格为通过条件。测试没有使用旧 viewer，也没有为场景生成区域网格。

`check.cjs` 在实际 Chrome WebGL 2 上绘制五种固定场景。每个场景比较分层跳跃和逐格遍历的完整像素结果，检查遍历超限、WebGL 错误及跨格裁片。最后比较两种玻璃厚度，并检查填满立方体的矩形窗口能否正确离开边界。

## 输入与实测

2026-11-15 在 Apple M4、Chrome ANGLE Metal 上执行。画布为 1280×720，像素比 1，关闭 MSAA。窗口为 64×32×64，输入由 `scene.go` 中的 `BuildScene` 固定生成。前四个场景相机为 `(32,16,58)`，朝向 `(32,3,25)`；裁片场景相机为 `(32,4,31)`，朝向 `(32,3,26)`。FOV 为 65°。

以下数据由工作区根目录执行 `node neomega-r2/experiment/check.cjs` 得到。每个场景等待至少 90 个有效 GPU 查询结果，舍弃前 30 个样本，使用剩余样本统计。测试启动一个浏览器页面并顺序切换场景，共享模型资源只加载一次。这是单次静态视点测量，不能当作真实存档的帧率保证。

| 场景 | 非空气格子 | GPU 中位数 | GPU P95 | 层次与逐格画面的最大通道差 |
|---|---:|---:|---:|---:|
| 综合方块 | 8507 | 5.991 ms | 7.573 ms | 0 |
| 密集栏杆 | 10112 | 11.701 ms | 13.959 ms | 0 |
| 密集花朵 | 10112 | 7.466 ms | 7.633 ms | 0 |
| 完整立方体 | 10112 | 3.955 ms | 4.020 ms | 0 |
| 跨格裁片 | 8200 | 5.671 ms | 5.938 ms | 0 |

GPU 纹理分配约为 29.5 MiB，包含全部共享静态模型、两个图集、该小型窗口及其层次，不包含帧缓冲和驱动内部开销。Go 场景构造约 5.3～5.9 ms，但这个时间包含实验方块的挑选与索引填写，不能替代真实存档解码和加载测量。

完整结果与采样值见 [results.json](results/results.json)，画面见 [综合场景](results/showcase.png) 和 [预裁片场景](results/fragments.png)。未与旧 viewer 的优化网格进行性能对照，也未在 Windows/D3D 后端验证。

## 正确性检查

五个场景没有出现遍历超限像素，WebGL error 为 0，页面没有异常。关闭跨格片段后，裁片场景有 12996 个像素发生变化，确认伸出源格子的表面实际由目标格子绘制。

玻璃测试使用 1×1 画布，使两种厚度沿同一条正面射线采样最低 mip。8 格和 16 格厚度均得到 RGBA `[162,188,205,255]`，没有随厚度累积加深。该测试验证的是介质边界规则，不代表两个不同厚度的物体在所有透视像素中外观完全相同。

Go 测试另外验证裁切保留总表面积与 UV、生成的全部通用三角面都位于单位格内，以及同一格能同时保留自身模型和来自不同方块的裁片索引。

## 复现命令

从工作区根目录运行服务：

```sh
go run ./neomega-r2/cmd/r2 -listen 127.0.0.1:2413
```

另一个终端执行：

```sh
./check.sh neomega-r2
node neomega-r2/experiment/check.cjs
```

脚本输出到 `/tmp/r2-check`。测试其他地址时设置 `R2_URL`；测试工具路径通过 `PLAYWRIGHT_MODULE` 和 `CHROME` 指定。场景、分辨率或采样策略改变后，应重新生成结果。

## 继续验证的重点

这组输入证明了静态方块可以共用一条射线路径，还没有验证大窗口流式加载、分区边界的裁片生命周期、动态对象、动画和复杂表面的远距离过滤。密集栏杆的成本高于完整立方体，说明单格内的模型求交仍值得关注。后续优化可以围绕共享模型内部的加速结构进行，不必重新引入网格与射线的交接。
