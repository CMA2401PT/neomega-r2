# neomega-r2：统一的格子射线渲染核心

R2 用同一条射线管线绘制完整方块、复杂静态方块和活动部件。射线先穿过空间格子，再检查格内登记的表面：立方体直接求命中面，复杂模型检查登记到该格的四边形，活动部件把射线变换到局部坐标求交。所有命中共用排序、光照和透明合成。

本模块提供共享模型、场景准备器、WebGPU 与 WebGL 2 绘制器、世界会话以及特殊对象接口。世界会话按相机位置决定需要哪些区域，向数据源订阅并把收到的数据准备、上传到 GPU；数据从哪里来由宿主实现数据源决定，核心自带内存数据源与 R2Link 数据源。[neomega-viewer-r2 应用](../../apps/neomega-viewer-r2/README.md) 负责存档读取与来源选择。Viewer 和内存 demo 共用 `common_ui/` 的相机操作、地图、设置及绘制循环。核心不依赖 `celler`、旧 viewer 或任何应用模块；`demo/` 是不需要后端的验证页，场景放在内存世界里。

浏览器部分用 TypeScript 编写，源码在 `src/`，`npm run build` 输出到 `dist/`，目录结构与 `src/` 相同，着色器按模块地址相对加载。渲染器的宿主从 `dist/index.js` 导入。`dist/` 不进入版本库；Go 程序嵌入它，所以 `go build` 之前要先构建一次。

`createRenderer(canvas, options)` 默认使用 WebGPU。指定 `{ useWebGPU: false }` 可选择 WebGL 2。宿主可以读取 `renderer.backend`，使用 `await renderer.pick(...)` 和 `await renderer.pixels()` 在两个后端读回结果。显式要求等待 GPU 完成时，使用 `await renderer.draw(camera, { ...options, synchronize: true })`。WebGPU 需要安全上下文，在线页面使用 HTTPS 或 localhost。构建时 `webgl2gpu/convert.cjs` 从同一份 GLSL 射线程序生成四档 WGSL，各档在浏览器中按需创建管线。两个后端都有独立的实时累积、照片和拾取程序。实时累积固定一次反弹，多次反弹照片按需编译。WebGL 与预览并行编译对应的拾取程序，让首次点击也能同步返回。光影与累积共用同一份射线循环，主射线、反射和反弹都从同一处调用体素遍历，以减少驱动内联时复制的代码。

## 共享查看界面

静态 demo 与 Go Viewer 都在页面中加载 `/r2/common_ui/style.css` 和 `boot.js`。启动脚本挂载 `layout.html`，再导入宿主通过 `data-entry` 指定的模块。宿主可用 `<template id="actions">` 添加底栏按钮，用 `<template id="settings-extra">` 添加专属设置。

宿主把渲染器、相机和设置交给 `createView()`，在动画循环中调用 `view.frame(now, session)`。切换世界时调用 `view.setWorld()` 并提供区块占用表，地图就能缩放到区块概览。demo 从内存场景生成占用表，Viewer 通过 R2Link 请求。两个宿主的接入示例分别在 [demo/main.ts](demo/main.ts) 和 [Viewer 的 app.ts](../../apps/neomega-viewer-r2/web/app.ts)。

## 数据怎样到达屏幕

模型解析只在生成资源时进行。每个方块状态得到共享模型编号，完整立方体引用六面贴图，复杂模型引用一组四边形。四边形不裁切：它覆盖到的每个格子都登记一条引用，着色器只接受落在当前格射线区间内的交点。伸出本格的模型（告示牌、高墙）因此成为目标格的片段，射线不必搜索邻居。

每条四边形引用只有 16 字节，存法线和平面常数，射线先用它求平面交点；只有交点落在本格内，才读取存放贴图坐标与材质的记录。相同内容的记录由多个格子共享。

运行时来源提供压缩子区块（subchunk，原名 section）。每个子区块存储 16×16×16 个方块；每块包含调色板和压缩格子索引。调色板的每项是 Java 方块状态的 neomega-blocks 哈希（u32），渲染器按资源包的 `states.bin` 换成共享静态模型编号，表外的哈希画成空气并计入 unknown。完整立方体、栏杆、楼梯、花等使用同一套模型，不按距离替换形状。准备器为每个 section 生成目录项和空域掩码，并登记复杂片段和活动对象。

```text
共享资源：模型 → 四边形引用与记录、方块面贴图数组、静态模型编号
来源适配：压缩 section → 调色板编号映射
场景准备：登记片段和实例 → section 目录项、小块掩码与格子掩码
GPU 发布：上传单个区域 → 更新目录 → 回收旧地址
每帧绘制：遍历候选格 → 求交 → 采样 → 按命中顺序合成
```

射线遍历的代价主要是每一步的显存读取次数，所以空域按三级组织。目录每个 section 一项：整块相同的 section 只存一个模型编号，射线再沿上层的均匀层次一次跨过更大的空间；其余 section 的目录项带一张 64 位掩码，标出哪些 4×4×4 小块有内容。小块整体为同一完整方块时直接给出编号，否则再用 64 位掩码标出有内容的格子。空小块和空格子都在寄存器里判断，只有命中有内容的格子才读取压缩索引。射线在同一 section 和同一小块内移动时复用已读取的目录项和掩码。

完整方块的面贴图放在纹理数组中，带预先生成的 mip。着色器按相邻像素射线在面上的距离选择 mip 级：级内取最近像素，保持与游戏一致的硬边；级间线性混合，远处纹理不会闪烁。斜看的面沿足迹长轴最多取 4 个点平均，代替会带来双线性模糊的硬件各向异性过滤。远景因此不需要另存一份颜色。复杂模型目前从图集读取首帧，尚未做缩小过滤。

树叶、铜格栅这类贴图带洞的完整方块单独成类。射线每进入一格就检查入射面，打在洞上就继续前进，所以相邻树叶之间的面也看得见。它们不能合并成均匀节点，树冠因此要逐格遍历。射线每穿过一层叶子的空隙，后方颜色变暗一些，以此近似游戏里树叶逐格削弱天光；穿出树冠、进入成块的空域后恢复。

## 绘制器怎样接收相机与拾取

`createRenderer(canvas)` 创建共享模型和 GPU 资源，宿主负责调用 `draw(camera, options)` 推进画面。没有安装世界时，也可以绘制受太阳方向影响的天空与解析海面。卸载世界后也可以继续转向、绘制和拍照。

相机用 `position` 指定世界位置，用弧度制的 `yaw`、`pitch` 指定朝向。yaw 为零时看向北方（−Z），pitch 为正时向上看。默认使用垂直视场 65° 的透视投影，所有像素射线从相机位置发散。设置 `ortho` 后改用正交投影，数值表示画面高度覆盖多少方块。正交射线方向都相同，起点沿像平面平移，因此地图从高空观察时不会出现近大远小。纹理过滤也使用恒定的像素足迹。

每帧可以传入 `objects: false` 隐藏特殊对象，静态模型仍完整绘制。这个选项只作用于该次绘制，不改变对象仓库或其他视图的开关。

需要大片开放水域时，传入 `ocean: 64`，就会在世界高度 y=64 处绘制无限海面，窗口外也有水。省略 `ocean` 时使用场景本身的体素水。海面是独立的解析平面，不需要向来源区域填入水方块；它与体素水用于不同场景。`draw` 和 `photograph` 都接受这个选项，海面不参与 `pick`。

`photograph` 接受与 `draw` 相同的投影、对象和海面选项。相机、光照、海面高度、对象选项或世界版本改变时，宿主应使用 `accumulate: false` 开始新画面。`time` 以秒控制波纹的流动；每个累积序列保留预览开始时的水面时刻，因此静止采样会保留波纹碎片。需要动画时，宿主持续传入新时刻并绘制预览。

地图用 `pick(camera, { width, height, x, y })` 查询某个像素主射线最先遇到的表面。像素从左上角起算，坐标零表示首个像素，查询位置取像素中心。传入的宽高必须与查询坐标使用同一单位，可以使用 CSS 像素或实际渲染像素。返回值是 `{ position, normal }`，分别为整数方块坐标和朝向射线来处的几何法线；没有命中则返回 `null`。透明孔洞会继续穿透，水和玻璃的首个可见界面可以选中。拾取只检查静态世界，适合地图选点。

拾取使用同一着色器在一个 RGBA32F 浮点像素上写入距离与法线，再同步读回。宿主不必维护另一套 CPU 模型求交。方块坐标由命中点沿法线向内退少许再取整得到，避免把边界误认成邻格。拾取不改动画面或累积样本数。

```js
const camera = {
  position: [1280, 2000, 1800],
  yaw: 0,
  pitch: -70 * Math.PI / 180,
  ortho: 320,
};
renderer.draw(camera, {
  width: 1280,
  height: 720,
  objects: false,
  fog: Infinity,
});
const selected = renderer.pick(camera, {
  width: 1280,
  height: 720,
  x: 640,
  y: 360,
});
```

## 光照怎样计算

R2 把光照分为表面自身发出的光，以及从别处到达表面的光。每个像素先发一条主射线，按命中顺序合成颜色；需要更多光照信息时，再从命中点分出阴影、反射或反弹射线。这些射线都复用场景遍历，只是起点、方向与经过的介质不同。

太阳或月亮提供方向光。太阳落到地平线以下时换成月亮，方向由调用方传入。主射线上最主要的受光面向光源发一条阴影射线。镂空面按贴图判断透光，玻璃按代表色过滤，因此染色玻璃可以投下彩色影子。天空是随太阳高度变化的解析渐变，黄昏时朝太阳一侧偏橙；环境光取天空的平均亮度。夜里的星点按世界方向生成，位置与相机平移、时间和样本随机种子无关。星点按像素角宽过滤，转动相机时保持稳定。太阳、月亮和星星都能出现在水面反射里。

发光材质直接把线性颜色乘以自发光强度加到亮度上。原版海晶灯、萤石、菌光体、三种蛙明灯的侧面与顶面，在资源合成时获得 labPBR 高光贴图 A=190；点亮的红石灯为 A=170。着色器使用 `A / 254 × 1.6` 作为发光倍数，因此灯块的原始色彩和纹路仍参与发光。材质包提供 `_s` 时覆盖这个默认值，A=255 按 labPBR 约定表示不发光。预生成资源与运行时切换材质包共用同一个合成器。

玻璃和体素水使用同组介质的边界规则，内部接缝不重复着色。水中的光按路程指数衰减，每格红、绿、蓝的消光系数分别为 `(0.28, 0.075, 0.05)`。红光消失得最快，水下的灯块因此偏蓝绿，距离再远就只剩水体散射。

解析海面在主射线到达水位时分出反射与折射。菲涅耳反射率决定两者的比例：正视水面约反射 2%，掠射时反射更强。反射射线命中世界就读取表面亮度，未命中就读取天空；折射按空气与水的折射率 1:1.333 改变方向，再沿水下路径求交。窗口外到入口的水下距离也计入吸收。这样海面延伸到地平线，没入水中的发光几何仍能透出来。相机在水下时，出水射线按平面折射，超过临界角则全反射。

涟漪只改变着色法线，水面几何保持平面。16 个不同方向与尺度的行波叠加成斜率场，波长约为 0.27–57 格，波速随尺度变化。每个波都根据像素在水面上的足迹衰减；这个足迹包含距离和掠射造成的拉伸。可分辨的波保留成清晰碎片，滤掉的斜率方差则转成反射粗糙度，避免远处出现摩尔纹。

画面有两档质量。移动时的预览沿平均法线发一条反射射线，再发一条折射射线；法线扰动使反射落到几何平面下方时，预览把方向折回上方，避免单法线近似产生黑缝。静止后的累积以斜率均方根作为分布宽度，采样朝向相机的 [GGX 微面](https://jcgt.org/published/0007/04/01/)，并计入 Smith 遮蔽；它把像素内无法分辨的细波统计成柔和的反射分布，所以灯光倒影逐渐形成拉长的光带。折射使用过滤后的平均法线，水下轮廓因此保持稳定。海面预览的额外遍历最多为一条反射与一条折射。

普通表面的预览使用常量环境光，并按朝向打折，让侧面和朝下的面略暗。累积时，每一帧作为一个样本加入画面：像素内抖动消除锯齿，阴影方向在光源圆盘内抖动得到软影，主要表面的常量环境光则换成反弹射线看到的亮度。反弹命中发光面时会带回自发光，发光方块因此能够照亮周围。反弹到海面时也按反射和折射合成。

## 四档渲染器

同一份射线源码按 `RENDER_TIER` 编译成四个 GPU 程序，从低到高为：

| 档 | 名字 | 内容 |
| --- | --- | --- |
| `voxel` | 体素渲染器 | 每个非空格子都是立方体：完整方块每面一种代表色，其余模型整体一种平均色；水、玻璃这类表面是透明纯色块。没有贴图、阴影、雾和水面效果。 |
| `basic` | 基础渲染器 | 完整的方块形状与贴图，透明与镂空照常处理；水按玻璃那样的透明介质处理，无限海面是一层透明的水色平面。没有阴影、雾、波纹、反射和 labPBR 法线。 |
| `shading` | 光影渲染器 | 上面各节描述的预览：阴影、雾、波纹海面、反射与折射、labPBR 材质。 |
| `accumulation` | 累积渲染器 | 光影渲染器加上像素内抖动、软影与反弹光，每帧累积一个样本。 |

前三档用于预览，宿主按设备能力选一档；静止累积和拍照总是使用累积渲染器。体素、基础两档为手机等较弱的设备准备，程序更小、编译更快。`createRenderer(canvas, { tier })` 启动时只编译这一档（默认 `shading`），其余各档用 `compile(tier)` 在需要时编译，`ready(tier)` 查询是否可用。编译前绘制器会先让出两帧，宿主写在页面上的提示因此能在编译阻塞页面之前显示出来。各档共享纹理、世界目录和累积缓冲，切换时只更换程序与 uniform 位置。

`draw(camera, { tier })` 选择预览档，默认 `shading`；所需的档还没编译好时 `draw` 返回 `false`，宿主可以继续用上一档。`accumulate: true` 时 `draw` 用累积渲染器。`pick` 使用已编译的最高预览档。

材质包带有 labPBR 数据时（见下一节），`_n` 的法线按贴图坐标方向转到世界空间。漫反射和直射高光使用扰动后的法线，几何上背光的面仍不受直射。F0 表示正入射反射率，它与粗糙度共同决定 GGX 高光。累积时，反弹按漫反射与镜面的权重选择方向，光滑表面因此映出周围。金属以自身颜色为反射率，没有漫反射。高度与孔隙／次表面通道不参与着色。

远处的体素表面按首个命中的距离混入天空颜色。雾随距离的八次方变浓，近处几乎没有，在调用方给出的雾距离处接近不透明，用来遮住观察窗口的边界。无限海面自身不依赖这个边界。

累积缓冲使用 32 位浮点，保存亮度与权重之和。显示时相除，再把 7.5% 的亮度分散到六级模糊光晕中，最后做曝光和 ACES 色调映射。曝光从白天的 0.9 平滑提高到夜间的 2.97，让暗海仍可见，同时保留灯块的浅色纹路。

拍照在离屏缓冲里进行，可以指定尺寸与反弹次数（最多 4 次）。默认使用累积渲染器，样本没有上限，宿主满意时取图。传入预览档的 `tier` 时用于导出当前画面：每个像素按 `supersample`×`supersample`（默认 4×4）的固定网格偏移重画，取满后 `complete` 变为真。画面切成 256 像素见方的小块分批提交，避免单批占用 GPU 过久。宿主每帧调用一次 `step()`，绘制器用 GPU 栅栏判断上一批是否完成，并据此调整批量；`present()` 把当前结果显示到画布上，`png()` 取图：

```js
const photo = renderer.photograph(camera, {
  width: 2560,
  height: 1440,
  tier: "basic",
  supersample: 4,
  sun,
  fog,
  ocean: 64,
  time: 12,
});
// 每个动画帧：
photo.step();
photo.present();
if (photo.complete) download(await photo.png()), photo.dispose();
```

## 材质包怎样替换贴图

Java 材质包通过资源名字替换共享静态模型的贴图，例如 `minecraft:block/stone` 对应包根目录下的 `assets/minecraft/textures/block/stone.png`。核心接受 zip 或目录，缺失和无法解码的单张图片使用原版。颜色、透明度派生表与 labPBR 数据在 Go 端一起合成，浏览器收到完整结果后再上传。

一个方块面可能由底图和覆盖层组成。生成资源时保留每层的名字、UV 方向与染色，草方块侧面的泥土和草边因此能够分别替换。每次合成都从原版基表开始，重新计算代表色、镂空立方体分类和复杂模型的 alpha 裁切模式。模型编号保持不变，存档调色板可以继续使用。活动对象的私有贴图由对应外观工厂提供。

labPBR 是把材质属性编码到配套图片中的约定。同名 `_n.png` 保存法线 RG、AO 的 B 和高度 A；`_s.png` 保存光滑度、F0／金属、孔隙／次表面和自发光。缺图时法线填 `(128,128,255,255)`，高光填 `(0,0,0,0)`；上一节列出的原版灯块使用对应的自发光 A。这些通道都是数据，因此使用 RGBA8 原值上传，不经过 sRGB 转换或 alpha 预乘。

完整方块使用颜色、法线和高光三张纹理数组，三者的层号、边长和 mip 布局一致。数组边长取所用替换图片的最大边长，向上取二次幂，再限制到调用方指定的上限；原版基准为 16，上限默认 128，可选 16、32、64、128、256、512。小图按最近点放大，大图按覆盖面积缩小。颜色 mip 在线性预乘空间逐级平均，再编码为 SRGB8_ALPHA8；数据 mip 直接平均四个通道。带 `.mcmeta` 的动画按帧列表取首帧，未列帧序时取第 0 帧。

复杂模型的三张图集共用装箱区域，保留各张图片的宽高比，在同一上限内缩放。图集颜色使用未预乘的 RGBA8，由着色器转线性；法线和高光仍保留原值。完整方块的三张数组由 `uSurfaces`、`uSurfaceNormals`、`uSurfaceSpecular` 读取，复杂模型对应 `uAtlas`、`uAtlasNormals`、`uAtlasSpecular`。上传与释放集中在 [textures.ts](src/render/textures.ts)，纹理单元依次为数组 6／7／9、图集 5／0／14。

宿主只需调用 `neomega-view-utils/r2assets` 的 `BuildTextures(path, maxSize)` 得到 `TextureSet`；空路径表示原版，尺寸上限为零表示默认值。返回值包含图片和匹配的共享模型表，可以用 `set.WriteTo(writer)` 写成单个二进制响应。浏览器通过 `decodeTextures(buffer)` 解码，再交给 `renderer.setTextures(set)` 上传。应用的切换流程还会让后台准备器用新分类重建已显示区域，并在同一帧发布空间目录和贴图；准备期间继续显示旧场景。

仅三张数组的显存为 `563 × 4 × 3 × (S² + (S/2)² + … + 1)` 字节，其中 `S` 是实际层边长。图集另占 `宽 × 高 × 4 × 3` 字节，共享模型表、实例贴图和场景池另计。

## 世界会话与数据源

宿主创建渲染器后，用一个数据源创建 `WorldSession`，并在每帧调用 `focus` 与 `publish`：

```ts
const session = new WorldSession(renderer, source, { registry });
function frame() {
  session.focus(camera.position, { nearRadius: 4, farRadius: 32 });
  session.publish();
  renderer.draw(camera, { width, height, tier: "shading" });
}
```

会话以 r2region 为单位订阅和发布。一个 r2region 横向覆盖 8×8 个区块（chunk），每个区块沿高度包含多个子区块（subchunk）。协议消息中的 `region` 指一个 r2region。`focus` 根据远景半径算出可见窗口内的区域，加上窗口外一圈用于接收伸入片段的邻接区域，再算出近景半径内需要特殊对象的区域；只有集合变化时才调用一次 `source.want`，告知增减：

| 字段 | 含义 |
|---|---|
| `center` | 远景中心的方块坐标 `[x, z]`，数据源排队时可先供给离它近的区域。 |
| `regions.add` / `remove` | 新需要、不再需要的区域，`add` 由近到远排列。 |
| `objects.add` / `remove` | 需要特殊对象的区域，带近景圆心（区块坐标）与半径。已需要的区域再次出现在 `add` 里，表示圆心或半径变了。 |

数据源通过 `open` 收到的 `WorldSink` 交付数据：`region(x, z, data)` 提交区域方块，`data` 为 `null` 表示区域为空；`objects(x, z, descriptors)` 提交近景对象；`error(x, z, err)` 把区域标为失败。同一区域可以重复提交，会话用新内容替换，旧画面保留到新内容准备完成。不再需要的区域的提交被忽略，数据源不必处理竞态，但应尽早取消对应的工作。`want` 是唯一的订阅方式，会话不会主动拉取。

收到的数据在后台线程缓存，按离相机由近到远逐个准备；`publish` 每帧最多上传一个准备好的区域。`session.stats` 给出窗口内区域数、已显示数、等待数、近景未完成数、显存占用和未知方块数；`published(x, z)` 告诉宿主区域是否已经可以拾取。`dispose` 关闭数据源、结束线程并释放对象。

### 区域编码

`region` 提交的数据是小端 u32 数组：

```text
magic 0x34504c54, section 数
每个 section：
  sx, sy, sz          section 坐标（方块坐标除以 16，有符号）
  bits                每个索引的位数，0 表示整块只有调色板第一项
  count               调色板项数
  length              索引字数
  palette[count]      方块状态的 neomega-blocks 哈希
  words[length]       索引，每字容纳 floor(32 / bits) 个，低位在前，不跨字
```

section 内第 i 个索引对应格子 `x = i >> 8, z = (i >> 4) & 15, y = i & 15`。未列出的 section 视为空气。世界高度固定为 -64 到 448（32 个 section）。

### 内存世界

不读存档的宿主（验证页、测试、小工具）可以把方块写进 `MemoryWorld`，再用 `memorySource` 交给会话。方块状态用 Java 写法，`blockHash` 把它换成与 Go 的 `BlockToHash` 相同的哈希：

```ts
const world = new MemoryWorld();
world.fill([0, 0, 0], [63, 0, 63], "minecraft:stone");
world.set(4, 1, 4, 'minecraft:oak_fence ["east"="true","west"="true"]');
world.addObject({ key: "book", kind: "enchanting_book", position: [4, 2, 4] });
const session = new WorldSession(renderer, memorySource(world), { registry });
// 之后的修改在 commit 时提交，正在显示的区域重新准备：
world.set(4, 1, 5, "minecraft:glass");
world.commit();
```

`memorySource` 在下一个微任务交付需要的区域；`commit` 只重新提交方块或对象有变化、且仍被需要的区域。对象按近景圆心与半径筛选，规则与 Go 的 `worlddata.Objects` 相同。自己实现数据源时，可以用 `encodeRegion(sections)` 把每个 section 的 4096 个哈希编码成上面的格式。

### R2Link 数据源

数据源也可以是另一个进程：游戏机器人、服务器插件或存档服务监听 WebSocket，浏览器用 `r2linkSource` 连接。会话的每次 `want` 变成一条消息，数据源回送区域、对象和相机指令，协议见 [neomega-r2link](../go-link/README.md)：

```ts
const source = r2linkSource("ws://127.0.0.1:2414/r2link", {
  onCamera: (camera) => moveCamera(camera),
  onState: (state, message) => showConnection(state, message),
});
const { scene, camera } = await source.welcome; // 首次连接失败时拒绝
const session = new WorldSession(renderer, source, { registry });
```

断线后保留已显示的内容，每 3 秒重连；重连握手后重新发送完整的订阅，数据源重发全部内容。`source.chunks()` 请求区块占用表，供地图显示世界分布；`source.clippedSections` 是数据源报告的超高 section 数。

## 模块边界

为了让来源和绘制互不牵制，浏览器部分以纯数据为边界，公共数据类型见 [contracts.ts](src/contracts.ts)，公开入口为 [index.ts](src/index.ts)。

| 位置 | 责任 |
|---|---|
| `neomega-view-utils/r2assets` | 默认资源包（共享状态、模型、贴图与四边形资源）；读取材质包、重建三通道贴图及透明度派生表。核心只依赖资源包的文件格式。 |
| `src/render/textures.ts` | 解码完整贴图集，上传和释放共享 GPU 纹理。 |
| `src/scene/prepare.ts` | 接收压缩区域与候选对象，生成可上传数据；不读取 UI，不持有 WebGL。 |
| `src/scene/worker.ts` | 在后台线程缓存来源区域并调用准备器；不决定加载范围。 |
| `src/session/session.ts` | 由相机位置决定需要的区域和近景对象，向数据源订阅，排队准备并逐帧发布；不知道数据来自哪里。 |
| `src/source/` | 方块状态哈希、区域编码、内存世界数据源和 R2Link 数据源。 |
| `src/render/world-gpu.ts` | 管理循环区域目录、增量上传与地址回收。 |
| `src/render/renderer.ts`、`ray.frag` | 接收相机和帧参数，执行统一射线绘制；不读取存档。 |
| `src/objects/`、`src/effects/` | 通用实例资源管理及各类外观、动画实现。 |
| `common_ui/` | 可选的 TypeScript 查看界面，两种宿主共用 HUD 布局、CSS、飞行控制、地图、拍照和渲染状态。 |
| `demo/` | 固定验证场景与最小宿主，经内存数据源走和存档相同的会话路径。 |

场景准备以 8×8 区块为一个区域，收集目标区域及相邻来源伸入的片段。整个可见窗口边缘保留邻接来源区域，以接收窗口外模型伸入的片段。来源加载卸载或活动对象候选变化时，宿主重新准备受影响的目标区域；近景半径本身不参与静态准备。准备结果包含相对地址及重定位位置，显存分配器在上传时转换地址。移动窗口使用循环目录，不搬动仍在范围内的数据；同一帧内先上传完成的区域，再切换目录，最后回收旧地址。

GPU 的目录覆盖容量为 4096×4096×512，宿主使用不超过这个容量、按 128 方块对齐的观察窗口。默认区域池为 256 MiB；释放区域回收池内地址，关闭世界释放整个池。容量耗尽会报告错误，由宿主降低范围或调整容量。

## 怎样添加 effector 和 block actor

两类对象共用一个绘制入口，区别在于描述从哪里来。effector 仅根据方块状态和位置创建外观；block actor 还需要方块实体 NBT，例如旗帜图案或告示牌文字。来源只在近景调用已注册的处理器，远景保留共享静态模型本体。例如附魔台一直显示台座，活动书只在近景加载。

添加实现需要连接两端：

1. 数据源输出对象描述（稳定标识、类型、位置和该类型的数据）。Go 数据源可用 [neomega-r2link](../go-link/README.md) 的 `effector` 添加构造器，或在 `blockactor` 实现 `Handler`，得到 `object.Descriptor`。
2. 浏览器端添加外观工厂，返回贴图、局部盒体、动画包围盒和逐帧变换。特效放在 `src/effects/`；NBT 外观可在 `src/blockactors/` 按类型增加文件。
3. 数据源注册处理器，浏览器入口通过 `ObjectRegistry` 注册同名工厂。绘制循环无需添加方块类型判断。

[附魔书](src/effects/enchanting-book.ts) 是现有实例：七个盒体共享贴图，逐帧只更新变换。`ObjectStore` 管理实例槽、私有贴图和生命周期，场景准备器把包围盒覆盖的格子登记为候选，着色器在格内求交。句柄带代数，卸载后的旧格子引用不会误指向复用槽位的新对象。

包围盒必须覆盖整个动画，部件目前支持正交旋转、平移和统一缩放。贴图支持透明裁切。需要替换静态本体时，描述设置 `Replace`；实例准备完成后，本体格切换为实例，卸载后重新准备区域恢复静态模型。当前实现不涵盖任意变形网格和半透明活动部件；增加这些能力时应扩展通用部件求交，而不是在世界调度器加入特殊分支。

## 资源与运行

资源包及其生成工具位于 [assets-utils](../assets-utils/README.md)；渲染器通过 `assets` 选项给出的 URL 读取，验证页在 `/assets/` 提供默认资源包。

以下命令在包含 `go.work` 的工作区根目录运行。构建渲染核心和启动验证页需要 Node.js 22.18 以上版本，首次运行时先安装依赖。

```sh
npm --prefix neomega-r2/r2 ci
npm --prefix neomega-r2/r2 run demo
```

`demo` 先构建核心与验证页，再用 `scripts/serve.mjs` 提供静态文件：`/r2/` 是 `dist/`，`/assets/` 是默认资源包，其余是 `demo/`。另选地址时运行 `node scripts/serve.mjs 127.0.0.1:端口`。验证页只是静态文件，不需要 Go。

打开 <http://127.0.0.1:2415>，特殊对象场景为 `/?scene=special`。拖动转向，WASD 水平移动，空格上升、Shift 下降。底部坐标可直接编辑，Enter 或箭头按钮跳转，Esc 放弃。页面可选择渲染档、原生分辨率，以及用于对照的逐格遍历。要浏览真实 Java 存档，运行应用：

```sh
node apps/neomega-viewer-r2/scripts/build-web.mjs
go run ./apps/neomega-viewer-r2/cmd/viewer -listen 127.0.0.1:2412
```

资源重新生成与检查：

```sh
go generate ./neomega-r2/assets-utils
go vet ./neomega-r2/r2/... && go test ./neomega-r2/r2/...
npm --prefix neomega-r2/r2 run check
npm --prefix neomega-r2/r2 test
R2_URL=http://127.0.0.1:2415 node neomega-r2/r2/experiment/check.cjs
R2_URL=http://127.0.0.1:2415 node neomega-r2/r2/experiment/special.cjs
R2_URL=http://127.0.0.1:2412 node neomega-r2/r2/experiment/ocean.cjs
```

浏览器脚本需要 playwright：默认按 Node 的解析查找，也可以用 `PLAYWRIGHT_MODULE` 指向已有的模块目录；`CHROME` 指定浏览器，`R2_BROWSER_ARGS` 追加启动参数（例如 Windows 上的 `--use-angle=vulkan`），`R2_OUTPUT` 指定结果目录。浏览器回归验证玻璃厚度、跨格片段、矩形窗口的离开面、活动部件、透明孔与遮挡。`ocean.cjs` 连接应用的 Möbius 场景，固定夜间光照与水面时刻，输出预览、128 样本累积、照片、水下和窗口外视图，并检查拾取与累积时刻。GPU 查询与单像素同步读回耗时一起写到系统临时目录下的 `r2-ocean/results.json`，截图位于同一目录。

Java 存档流式更新与 GPU 对照见[应用的验收说明](../../apps/neomega-viewer-r2/experiment/README.md)。早期固定窗口研究的报告与数据见提交 `4a37e99`。
