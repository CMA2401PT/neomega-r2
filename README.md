# neomega-r2：统一的格子射线渲染核心

R2 用同一条射线管线绘制完整方块、复杂静态方块和活动部件。射线先穿过空间格子，再检查格内登记的表面：立方体直接求命中面，复杂模型检查登记到该格的四边形，活动部件把射线变换到局部坐标求交。所有命中共用排序、光照和透明合成。

本模块提供共享模型、场景准备器、WebGL 2 绘制器以及特殊对象接口。存档读取、HTTP 会话、连续加载、相机与界面由 [neomega-viewer-r2 应用](../apps/neomega-viewer-r2/README.md) 负责。核心不依赖 `celler`、旧 viewer 或任何应用模块；`cmd/r2` 是独立模型验证页。

## 数据怎样到达屏幕

模型解析只在生成资源时进行。每个方块状态得到共享模型编号，完整立方体引用六面贴图，复杂模型引用一组四边形。四边形不裁切：它覆盖到的每个格子都登记一条引用，着色器只接受落在当前格射线区间内的交点。伸出本格的模型（告示牌、高墙）因此成为目标格的片段，射线不必搜索邻居。

每条四边形引用只有 16 字节，存法线和平面常数，射线先用它求平面交点；只有交点落在本格内，才读取存放贴图坐标与材质的记录。相同内容的记录由多个格子共享。

运行时来源提供压缩 section。section 是 16×16×16 的存储块；每块包含调色板和压缩格子索引。调色板的每项给出一个共享静态模型编号，完整立方体、栏杆、楼梯、花等使用同一套模型，不按距离替换形状。准备器为每个 section 生成目录项和空域掩码，并登记复杂片段和活动对象。

```text
共享资源：模型 → 四边形引用与记录、方块面贴图数组、静态模型编号
来源适配：压缩 section → 调色板编号映射
场景准备：登记片段和实例 → section 目录项、小块掩码与格子掩码
GPU 发布：上传单个区域 → 更新目录 → 回收旧地址
每帧绘制：遍历候选格 → 求交 → 采样 → 按命中顺序合成
```

射线遍历的代价主要是每一步的显存读取次数，所以空域按三级组织。目录每个 section 一项：整块相同的 section 只存一个模型编号，射线再沿上层的均匀层次一次跨过更大的空间；其余 section 的目录项带一张 64 位掩码，标出哪些 4×4×4 小块有内容。小块整体为同一完整方块时直接给出编号，否则再用 64 位掩码标出有内容的格子。空小块和空格子都在寄存器里判断，只有命中有内容的格子才读取压缩索引。射线在同一 section 和同一小块内移动时复用已读取的目录项和掩码。

完整方块的面贴图放在纹理数组中，带预先生成的 mip。着色器按相邻像素射线在面上的距离选择 mip 级：级内取最近像素，保持与游戏一致的硬边；级间线性混合，远处纹理不会闪烁。斜看的面沿足迹长轴最多取 4 个点平均，代替会带来双线性模糊的硬件各向异性过滤。远景因此不需要另存一份颜色。复杂模型目前从图集读取首帧，尚未做缩小过滤。

树叶、铜格栅这类贴图带洞的完整方块单独成类。射线每进入一格就检查入射面，打在洞上就继续前进，所以相邻树叶之间的面也看得见。它们不能合并成均匀节点，树冠因此要逐格遍历。射线每穿过一层叶子的空隙，后方颜色变暗一些，以此近似游戏里树叶逐格削弱天光；穿出树冠、进入成块的空域后恢复。

## 光照怎样计算

每个像素先发一条主射线，按命中顺序合成颜色；需要更多光照信息时，再从命中点分出阴影、反射或反弹射线。这些射线都复用上面的场景遍历，只是起点和方向不同。

- 直射光来自太阳；太阳落到地平线以下时换成月亮，方向由调用方传入。主射线上最主要的受光面向光源发一条阴影射线：镂空面按贴图判断透光，玻璃按代表色过滤，染色玻璃因此投下彩色影子；水按光走过的距离吸收。
- 天空亮度是随太阳高度变化的解析渐变，黄昏时朝太阳一侧偏橙。环境光取天空的平均亮度。
- 玻璃和水采用同组介质的边界规则，内部接缝不重复着色，只在进出两个界面着色。两个界面之间按距离吸收：红光衰减最快，深水因此偏蓝绿。主射线从上方落到水面时再分出一条反射射线，反射比例按菲涅耳计算，水面法线由随时间变化的几组正弦波扰动。静态几何仍是完整高度的立方体。
- 远处按首个命中的距离混入天空颜色。雾随距离的八次方变浓：近处几乎没有，在调用方给出的雾距离处接近不透明，正好遮住观察窗口的边界。

画面有两档质量，共用同一个着色器。相机或场景变化时绘制预览：每像素一条主射线，环境光取常量，并按朝向打折（侧面和朝下的面通常被地面与周围挡住一部分），让预览的明暗接近收敛后的画面。静止以后，每一帧作为一个样本加到累积缓冲上：像素位置随机抖动以抗锯齿，阴影射线在太阳圆盘内抖动得到软影，主要表面的常量环境光换成一条反弹射线实际看到的亮度，墙角和屋檐下因此变暗。累积缓冲是 32 位浮点，保存“亮度×权重”与权重之和；显示时相除，再加泛光，最后做曝光和 ACES 色调映射。夜里曝光会自动提高。

拍照用同一套累积在离屏缓冲里进行，可以指定尺寸、每像素样本数和反弹次数（最多 4 次）。一个样本可能很慢，整张画面一次画完会在 Windows 上触发显卡超时重置，所以画面切成 256 像素见方的小块分批提交。宿主每帧调用一次 `step()`，绘制器用 GPU 栅栏判断上一批是否已完成，并据此调整批量；完成后用 `png()` 取图：

```js
const photo = renderer.photograph(camera, { width, height, samples: 1024, sun, fog });
// 每个动画帧：
if (photo.step()) download(await photo.png()), photo.dispose();
```

材质包带有 labPBR 数据时（见下一节），着色器按贴图坐标方向把 `_n` 的法线转到世界空间。漫反射和直射高光使用扰动后的法线，但几何上背光的面仍不受直射，法线贴图不会让它发亮。AO 只减弱环境光。F0 与光滑度给出 GGX 高光；累积时，反弹按菲涅耳的比例改走镜面方向，光滑表面因此映出周围。金属以自身颜色为反射率，没有漫反射。自发光直接加到颜色上，累积的反弹打到发光面时也会照亮周围。原版没有这些贴图，取默认值后与不带材质时一致。高度与孔隙／次表面通道目前不参与着色。

## 材质包怎样替换贴图

Java 材质包通过资源名字替换共享静态模型的贴图，例如 `minecraft:block/stone` 对应包根目录下的 `assets/minecraft/textures/block/stone.png`。核心接受 zip 或目录，缺失和无法解码的单张图片使用原版。颜色、透明度派生表与 labPBR 数据在 Go 端一起合成，浏览器收到完整结果后再上传。

一个方块面可能由底图和覆盖层组成。生成资源时保留每层的名字、UV 方向与染色，草方块侧面的泥土和草边因此能够分别替换。每次合成都从原版基表开始，重新计算代表色、镂空立方体分类和复杂模型的 alpha 裁切模式。模型编号保持不变，存档调色板可以继续使用。活动对象的私有贴图由对应外观工厂提供。

labPBR 是把材质属性编码到配套图片中的约定。同名 `_n.png` 保存法线 RG、AO 的 B 和高度 A；`_s.png` 保存光滑度、F0／金属、孔隙／次表面和自发光。缺图时分别填 `(128,128,255,255)` 和 `(0,0,0,0)`。这些通道都是数据，因此使用 RGBA8 原值上传，不经过 sRGB 转换或 alpha 预乘。

完整方块使用颜色、法线和高光三张纹理数组，三者的层号、边长和 mip 布局一致。数组边长取所用替换图片的最大边长，向上取二次幂，再限制到调用方指定的上限；原版基准为 16，上限默认 128，可选 16、32、64、128、256、512。小图按最近点放大，大图按覆盖面积缩小。颜色 mip 在线性预乘空间逐级平均，再编码为 SRGB8_ALPHA8；数据 mip 直接平均四个通道。带 `.mcmeta` 的动画按帧列表取首帧，未列帧序时取第 0 帧。

复杂模型的三张图集共用装箱区域，保留各张图片的宽高比，在同一上限内缩放。图集颜色使用未预乘的 RGBA8，由着色器转线性；法线和高光仍保留原值。完整方块的三张数组由 `uSurfaces`、`uSurfaceNormals`、`uSurfaceSpecular` 读取，复杂模型对应 `uAtlas`、`uAtlasNormals`、`uAtlasSpecular`。上传与释放集中在 [textures.js](web/render/textures.js)，纹理单元依次为数组 6／7／9、图集 5／0／14。

宿主只需调用 `r2.BuildTextures(path, maxSize)` 得到 `TextureSet`；空路径表示原版，尺寸上限为零表示默认值。返回值包含图片和匹配的共享模型表，可以用 `set.WriteTo(writer)` 写成单个二进制响应。浏览器通过 `decodeTextures(buffer)` 解码，再交给 `renderer.setTextures(set)` 上传。应用的切换流程还会让后台准备器用新分类重建已显示区域，并在同一帧发布空间目录和贴图；准备期间继续显示旧场景。

仅三张数组的显存为 `563 × 4 × 3 × (S² + (S/2)² + … + 1)` 字节，其中 `S` 是实际层边长。图集另占 `宽 × 高 × 4 × 3` 字节，共享模型表、实例贴图和场景池另计。

## 模块边界

为了让来源和绘制互不牵制，浏览器部分以纯数据为边界，公共数据类型见 [contracts.js](web/contracts.js)。

| 位置 | 责任 |
|---|---|
| `catalog.go`、`assets/` | 共享状态、模型、贴图与四边形资源。 |
| `textures.go`、`internal/texturepack/` | 读取材质包、重建三通道贴图及透明度派生表。 |
| `web/render/textures.js` | 解码完整贴图集，上传和释放共享 GPU 纹理。 |
| `web/scene/prepare.js` | 接收压缩区域与候选对象，生成可上传数据；不读取 UI，不持有 WebGL。 |
| `web/scene/worker.js` | 在后台线程缓存来源区域并调用准备器；不决定加载范围。 |
| `web/render/world-gpu.js` | 管理循环区域目录、增量上传与地址回收。 |
| `web/render/renderer.js`、`ray.frag` | 接收相机和帧参数，执行统一射线绘制；不读取存档。 |
| `object/`、`effector/`、`blockactor/` | Go 侧特殊对象描述、无 NBT 特效路由和需要 NBT 的外观处理器。 |
| `web/objects/`、`web/effects/` | 通用实例资源管理及各类外观、动画实现。 |
| `scene.go`、`cmd/r2`、`web/main.js` | 固定验证场景与最小宿主，不承担应用的世界调度。 |

场景准备以 8×8 区块为一个区域，收集目标区域及相邻来源伸入的片段。整个可见窗口边缘保留邻接来源区域，以接收窗口外模型伸入的片段。来源加载卸载或活动对象候选变化时，宿主重新准备受影响的目标区域；近景半径本身不参与静态准备。准备结果包含相对地址及重定位位置，显存分配器在上传时转换地址。移动窗口使用循环目录，不搬动仍在范围内的数据；同一帧内先上传完成的区域，再切换目录，最后回收旧地址。

GPU 的目录覆盖容量为 4096×4096×512，宿主使用不超过这个容量、按 128 方块对齐的观察窗口。默认区域池为 256 MiB；释放区域回收池内地址，关闭世界释放整个池。容量耗尽会报告错误，由宿主降低范围或调整容量。

## 怎样添加 effector 和 block actor

两类对象共用一个绘制入口，区别在于描述从哪里来。effector 仅根据方块状态和位置创建外观；block actor 还需要方块实体 NBT，例如旗帜图案或告示牌文字。来源只在近景调用已注册的处理器，远景保留共享静态模型本体。例如附魔台一直显示台座，活动书只在近景加载。

添加实现需要连接两端：

1. Go 端在 `effector/` 添加构造器，或在 `blockactor/` 实现 `Handler`，输出 `object.Descriptor`。描述包含稳定标识、类型、位置和该类型的数据。
2. 浏览器端添加外观工厂，返回贴图、局部盒体、动画包围盒和逐帧变换。特效放在 `web/effects/`；NBT 外观可在 `web/blockactors/` 按类型增加文件。
3. 应用在 Go 入口注册来源处理器，在浏览器入口通过 `ObjectRegistry` 注册同名工厂。绘制循环无需添加方块类型判断。

[附魔书](web/effects/enchanting-book.js) 是现有实例：七个盒体共享贴图，逐帧只更新变换。`ObjectStore` 管理实例槽、私有贴图和生命周期，场景准备器把包围盒覆盖的格子登记为候选，着色器在格内求交。句柄带代数，卸载后的旧格子引用不会误指向复用槽位的新对象。

包围盒必须覆盖整个动画，部件目前支持正交旋转、平移和统一缩放。贴图支持透明裁切。需要替换静态本体时，描述设置 `Replace`；实例准备完成后，本体格切换为实例，卸载后重新准备区域恢复静态模型。当前实现不涵盖任意变形网格和半透明活动部件；增加这些能力时应扩展通用部件求交，而不是在世界调度器加入特殊分支。

## 资源与运行

`cmd/build-models` 读取本模块保存的输入资源，生成共享表。模型、原始图集、材质表和附魔书资源来自 viewer-core `8afee71`，运行时不导入该模块。原始图集保存在 `sourceassets/atlas.png`；贴图名字直接取自 `sourceassets/geometry.nvtables` 中的 `Surface.Texture`，UV 与染色也来自同一份几何。生成器输出 `assets/textures.json` 的名字和合成配方，以及供每次合成使用的 `base-*` 原版基表；原版六张贴图由相同的合成器生成。许可证见 [LICENSE](LICENSE) 和 [资源说明](sourceassets/THIRD_PARTY_NOTICES.txt)。核心 Go 依赖仅为状态目录与 NBT 类型。

从工作区根目录启动验证页：

```sh
go run ./neomega-r2/cmd/r2 -listen 127.0.0.1:2415
```

打开 <http://127.0.0.1:2415>，特殊对象场景为 `/?scene=special`。拖动转向，WASD 移动，Q/E 升降。页面可选择原生分辨率，以及用于对照的逐格遍历。要浏览真实 Java 存档，运行应用：

```sh
go run ./apps/neomega-viewer-r2/cmd/viewer -listen 127.0.0.1:2412
```

资源重新生成与检查：

```sh
go generate ./neomega-r2
./check.sh neomega-r2
node --test neomega-r2/tests/*.mjs
R2_URL=http://127.0.0.1:2415 node neomega-r2/experiment/check.cjs
R2_URL=http://127.0.0.1:2415 node neomega-r2/experiment/special.cjs
```

浏览器回归验证玻璃厚度、跨格片段、活动部件、透明孔与遮挡。Java 存档流式更新的验收见应用的 `experiment/`。固定版本的旧 brickmap 对照数据保留在 [实验报告](experiment/README.md)，不代表当前应用的加载行为。
