# neomega-r2：统一的格子射线渲染核心

R2 用同一条射线管线绘制完整方块、复杂静态方块和活动部件。射线先穿过空间格子，再检查格内登记的表面：立方体直接求命中面，复杂模型检查登记到该格的四边形，活动部件把射线变换到局部坐标求交。所有命中共用排序、光照和透明合成。

本模块提供共享模型、场景准备器、WebGL 2 绘制器以及特殊对象接口。存档读取、HTTP 会话、连续加载、相机与界面由 [neomega-viewer-r2 应用](../apps/neomega-viewer-r2/README.md) 负责。核心不依赖 `celler`、旧 viewer 或任何应用模块；`cmd/r2` 是独立模型验证页。

## 数据怎样到达屏幕

模型解析只在生成资源时进行。每个方块状态得到共享模型编号，完整立方体引用六面贴图，复杂模型引用一组四边形。四边形不裁切：它覆盖到的每个格子都登记一条引用，着色器只接受落在当前格射线区间内的交点。伸出本格的模型（告示牌、高墙）因此成为目标格的片段，射线不必搜索邻居。

每条四边形引用只有 16 字节，存法线和平面常数，射线先用它求平面交点；只有交点落在本格内，才读取存放贴图坐标与材质的记录。相同内容的记录由多个格子共享。

运行时来源提供压缩 section。section 是 16×16×16 的存储块；每块包含调色板和压缩格子索引。调色板的每项给出一个共享静态模型编号，完整立方体、栏杆、楼梯、花等使用同一套模型，不按距离替换形状。准备器为每个 section 生成目录项和空域掩码，并登记复杂片段和活动对象。

```text
共享资源：模型 → 四边形引用与记录、方块面贴图数组、静态模型编号
来源适配：压缩 section → 调色板编号映射
场景准备：登记片段和实例 → section 目录项、小块掩码与格子掩码
GPU 发布：上传单个区域 → 更新目录 → 回收旧地址
每帧绘制：遍历候选格 → 求交 → 采样 → 按命中顺序合成
```

射线遍历的代价主要是每一步的显存读取次数，所以空域按三级组织。目录每个 section 一项：整块相同的 section 只存一个模型编号，射线再沿上层的均匀层次一次跨过更大的空间；其余 section 的目录项带一张 64 位掩码，标出哪些 4×4×4 小块有内容。小块整体为同一完整方块时直接给出编号，否则再用 64 位掩码标出有内容的格子。空小块和空格子都在寄存器里判断，只有命中有内容的格子才读取压缩索引。射线在同一 section 和同一小块内移动时复用已读取的目录项和掩码。

完整方块的面贴图放在纹理数组中，带预先生成的 mip。着色器按相邻像素射线在面上的距离给出梯度，硬件完成三线性与各向异性过滤，因此远处方块的纹理不会闪烁，也不需要另存一份远景颜色。复杂模型目前从图集读取首帧，尚未做缩小过滤。

玻璃、水采用同组介质的边界规则，内部接缝不重复着色，不随穿过厚度持续加深。水暂为完整高度的立方体。

## 模块边界

为了让来源和绘制互不牵制，浏览器部分以纯数据为边界，公共数据类型见 [contracts.js](web/contracts.js)。

| 位置 | 责任 |
|---|---|
| `catalog.go`、`assets/` | 共享状态、模型、贴图与四边形资源。 |
| `web/scene/prepare.js` | 接收压缩区域与候选对象，生成可上传数据；不读取 UI，不持有 WebGL。 |
| `web/scene/worker.js` | 在后台线程缓存来源区域并调用准备器；不决定加载范围。 |
| `web/render/world-gpu.js` | 管理循环区域目录、增量上传与地址回收。 |
| `web/render/renderer.js`、`ray.frag` | 接收相机和帧参数，执行统一射线绘制；不读取存档。 |
| `object/`、`effector/`、`blockactor/` | Go 侧特殊对象描述、无 NBT 特效路由和需要 NBT 的外观处理器。 |
| `web/objects/`、`web/effects/` | 通用实例资源管理及各类外观、动画实现。 |
| `scene.go`、`cmd/r2`、`web/main.js` | 固定验证场景与最小宿主，不承担应用的世界调度。 |

场景准备以 8×8 区块为一个区域，收集目标区域及相邻来源伸入的片段。整个可见窗口边缘保留邻接来源区域，以接收窗口外模型伸入的片段。来源加载卸载或活动对象候选变化时，宿主重新准备受影响的目标区域；近景半径本身不参与静态准备。准备结果包含相对地址及重定位位置，显存分配器在上传时转换地址。移动窗口使用循环目录，不搬动仍在范围内的数据；同一帧内先上传完成的区域，再切换目录，最后回收旧地址。

GPU 的目录覆盖容量为 4096×4096×512，宿主使用不超过这个容量、按 128 方块对齐的观察窗口。默认区域池为 256 MiB；释放区域回收池内地址，关闭世界释放整个池。容量耗尽会报告错误，由宿主降低范围或调整容量。

## 怎样添加 effector 和 block actor

两类对象共用一个绘制入口，区别在于描述从哪里来。effector 仅根据方块状态和位置创建外观；block actor 还需要方块实体 NBT，例如旗帜图案或告示牌文字。来源只在近景调用已注册的处理器，远景保留共享静态模型本体。例如附魔台一直显示台座，活动书只在近景加载。

添加实现需要连接两端：

1. Go 端在 `effector/` 添加构造器，或在 `blockactor/` 实现 `Handler`，输出 `object.Descriptor`。描述包含稳定标识、类型、位置和该类型的数据。
2. 浏览器端添加外观工厂，返回贴图、局部盒体、动画包围盒和逐帧变换。特效放在 `web/effects/`；NBT 外观可在 `web/blockactors/` 按类型增加文件。
3. 应用在 Go 入口注册来源处理器，在浏览器入口通过 `ObjectRegistry` 注册同名工厂。绘制循环无需添加方块类型判断。

[附魔书](web/effects/enchanting-book.js) 是现有实例：七个盒体共享贴图，逐帧只更新变换。`ObjectStore` 管理实例槽、私有贴图和生命周期，场景准备器把包围盒覆盖的格子登记为候选，着色器在格内求交。句柄带代数，卸载后的旧格子引用不会误指向复用槽位的新对象。

包围盒必须覆盖整个动画，部件目前支持正交旋转、平移和统一缩放。贴图支持透明裁切。需要替换静态本体时，描述设置 `Replace`；实例准备完成后，本体格切换为实例，卸载后重新准备区域恢复静态模型。当前实现不涵盖任意变形网格和半透明活动部件；增加这些能力时应扩展通用部件求交，而不是在世界调度器加入特殊分支。

## 资源与运行

`cmd/build-models` 读取本模块保存的输入资源，生成共享表。模型、图集、独立 mip 和附魔书资源来自 viewer-core `8afee71`，运行时不导入该模块。许可证见 [LICENSE](LICENSE) 和 [资源说明](sourceassets/THIRD_PARTY_NOTICES.txt)。核心 Go 依赖仅为状态目录与 NBT 类型。

从工作区根目录启动验证页：

```sh
go run ./neomega-r2/cmd/r2 -listen 127.0.0.1:2415
```

打开 <http://127.0.0.1:2415>，特殊对象场景为 `/?scene=special`。拖动转向，WASD 移动，Q/E 升降。页面可选择原生分辨率、每像素射线数，以及用于对照的逐格遍历。要浏览真实 Java 存档，运行应用：

```sh
go run ./apps/neomega-viewer-r2/cmd/viewer -listen 127.0.0.1:2412
```

资源重新生成与检查：

```sh
go generate ./neomega-r2
./check.sh neomega-r2
node --test neomega-r2/tests/*.mjs
R2_URL=http://127.0.0.1:2415 node neomega-r2/experiment/check.cjs
R2_URL=http://127.0.0.1:2415 node neomega-r2/experiment/special.cjs
```

浏览器回归验证玻璃厚度、跨格片段、活动部件、透明孔与遮挡。Java 存档流式更新的验收见应用的 `experiment/`。固定版本的旧 brickmap 对照数据保留在 [实验报告](experiment/README.md)，不代表当前应用的加载行为。
